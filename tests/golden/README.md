# Golden-набор: единственная метрика, которая описывает сам продукт

Всё остальное в этом репозитории уже под автоматикой: ruff, mypy, bandit,
pip-audit, coverage-gate, KG contract drift. А качество разбора инцидента —
то, ради чего копилот существует — до сих пор меряли шестью ручными «боевыми
прогонами» в README и 👍/👎 в Discord. Каждое изменение промпта или порядка
стадий оценивалось на глаз.

Этот набор закрывает дыру: 30 зафиксированных инцидентов, ожидания к ним и
метрики, которым CI не даёт просесть.

## Что здесь меряется, а что нет

Честность метрики важнее её величины, поэтому граница проведена явно.

| Режим | Где гоняется | Что меряет | Чего НЕ меряет |
|---|---|---|---|
| `replay` | каждый PR | детерминированный обвес вокруг модели | качество самой модели |
| `live` | по расписанию + вручную | качество разбора на текущих промптах | — |

**`replay`** подставляет записанные ответы LLM (`recordings/`) вместо вызовов
модели: без сети, без ключа, бесплатно и одинаково от прогона к прогону. Под
проверкой оказывается всё, что вокруг: правила фактов, anchor-грounding в
FactCritic, отбор выжившей гипотезы, сборка `ExecutionIntent`, политика
executor-гейта. Именно здесь жили реальные регрессии — см. combat runs 1–3 в
[`docs/RUNBOOK.md`](../../docs/RUNBOOK.md).

Чего `replay` **не** говорит: стал ли новый промпт лучше. Ответ-то записан от
старого. Такой вопрос решает только `live`.

## Устройство кейса

```yaml
id: 013_facts_oom_false_positive_guard
llm: false            # нужна ли LLM-цепочка (false = чистый инвариант)
incident: {...}       # payload алерта, как приходит из AlertManager
context:              # то, что в проде собирает stage_diagnose
  k8s_pod_state: {...}
  k8s_events: [...]
intent: {...}         # готовый ExecutionIntent — для инвариантов гейта
expect:
  facts: {oom_killed: false, process_crash: true}
  cause_contains: ["memory", "oom"]     # достаточно одного попадания
  cause_not_contains: ["oom"]           # анти-регрессия
  resolution: resolved | unresolved
  intent_action: restart_deployment
  gate: block | approve | auto | none
  intent_rejected: true                 # отказ ещё на валидации intent-а
```

Причина сравнивается по ключевым словам, а не дословно: корневая причина —
свободная проза, требовать точного текста бессмысленно.

## Состав набора

* **6 кейсов с LLM-цепочкой** — реальные инциденты (`source: real`) из истории
  разборов: notificator exit 139, DI-падение bot-service, statics-луп
  map-service, OOM бота в preupdate, латентность в prod, 5xx после выката.
* **6 инвариантов executor-гейта** — что бы ни ответила модель: prod блокируется,
  `*-db` блокируется как data-plane, `kube-system` и `replicas: 0` отвергаются
  ещё на валидации интента, а squad-scale **не** блокируется (иначе кнопка
  Apply бесполезна).
* **8 детерминированных кейсов на факты** — структурный OOM, guard от OOM
  соседнего пода при exit 139, FailedScheduling, корреляция с выкатом,
  давление на ноде, шум GenerationMismatch, честное «нет сигналов».
* **4 кейса на playbook-и** (021–024) — где restart/scale-кандидат должен
  появиться, а где нет.
* **6 реальных классов поломок сквадов** (025–030) — из live-RCA датасета
  24.09.2026 (31 починенный squad-medic инцидент), обезличенно: dirty-версия
  миграции, образа нет в реестре, нет GRANT-ов, мёртвая запись Orleans
  membership, нет ключа в секрете, падение нового ReplicaSet после выката.
  Проверяют, что факты не выдумывают OOM/падение процесса там, где контейнер
  не стартовал, и что restart-playbook не становится кандидатом там, где
  рестарт не лечит. Кейс 027 (GRANT-ы) — известная дыра: restart его сейчас
  матчит, ожидание `playbooks` не записано до появления precondition-а.

Инварианты и факты живут без LLM вообще (`llm: false`) — они обязаны
выполняться при любом ответе модели, поэтому их прогон стоит миллисекунды.

## Как гонять

```bash
# то же, что делает CI
python scripts/eval_golden.py --mode replay --check-baseline

# один кейс
python scripts/eval_golden.py --case 013_facts_oom_false_positive_guard

# реальная модель без ключа — через залогиненный `claude` (подписка)
LLM_BACKEND=claude_cli python scripts/eval_golden.py --mode live \
  --check-baseline --baseline tests/golden/baseline_live.json

# перезаписать эталонные ответы после осознанной смены промпта
LLM_BACKEND=claude_cli python scripts/eval_golden.py --mode record
```

## baseline

`baseline.json` — метрики последнего согласованного прогона. CI сверяет и
агрегат, и разрез по группам проверок: без разреза «плюс два новых кейса на
факты» замаскировали бы «минус один на гейт».

Поднимать baseline — осознанное действие (`--update-baseline`, отдельным
коммитом). Понижать — только вместе с объяснением, почему деградация
допустима.

`baseline_live.json` — отдельный эталон для `live` (`--baseline`). Сверять
живую модель с replay-эталоном нельзя: тот меряет обвес на записанных
ответах, и любая перефразировка модели читалась бы как регресс. В live-сводке
есть ещё `latency_s` (всего, максимум, по кейсам) — только для информации, в
сверку не входит. Расписание — `.github/workflows/eval-live.yml` на ARC-раннере,
бэкенд `claude_cli` с секретом `CLAUDE_CODE_OAUTH_TOKEN` (`claude setup-token`).
Пока `baseline_live.json` не зафиксирован, прогон меряет, но не сверяет.

## Когда кейс падает

1. **Провалилась проверка `fact:*` или `gate`** — сломался детерминированный
   слой. Это регрессия в коде, а не в модели; чинить код.
2. **Провалилась `cause_contains` / `resolution`** — в `replay` это тоже
   регрессия обвеса (записанный ответ не изменился, а вывод изменился). В
   `live` — сигнал, что промпт или модель стали хуже.
3. **`MissingRecording`** — цепочка вызовов изменилась (добавили агента,
   переименовали роль). Перезаписать: `--mode record`, и посмотреть глазами,
   что новые ответы не хуже.

## Пополнение набора

Каждый разобранный инцидент — кандидат в кейс, особенно тот, на котором
копилот ошибся: именно такие ловят регрессии лучше всего. Кейс на 20 строк
YAML стоит дешевле, чем повторный разбор той же ошибки через полгода.
