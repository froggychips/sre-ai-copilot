# Откуда берутся orphan-узлы: разбор на живом графе

> Замер 14.08.2026, прод-граф через MCP (`kg_query`) + `kubectl` по живым
> namespace. Все цифры ниже — не оценки, а результаты запросов.

Роадмап по KG ставил задачу «снизить orphan до 10%», подразумевая, что не
хватает **источников рёбер**. Разбор показывает другое: **77% orphan — это
вообще не приложения**, и связывать их не нужно. А там, где рёбра
действительно нужны, сигнал в кластере есть, но недоступен коду в текущем
виде.

## 1. Состав orphan

Всего orphan — 2977 из 4971 узлов app-scope (59.9%).

| Что это | orphan | доля |
|---|---|---|
| приложения | 672 | 22.6% |
| БД (дубль синтетического `db:*`) | 647 | 21.7% |
| headless (`-hl`, `-headless`) | 579 | 19.4% |
| metrics / exporter | 551 | 18.5% |
| backup CronJob | 409 | 13.7% |
| NATS-инфраструктура | 119 | 4.0% |

Служебные Service Helm-чартов (headless, metrics, backup, exporter) —
безрёберны **по построению**. Рисовать им рёбра бессмысленно: это не узлы
топологии, а точки доступа к одному и тому же приложению.

## 2. Одна БД — два узла в графе

```
синтетических узлов db:*           17
рёбер uses_db → к ним           4459
рёбер uses_db → к k8s Service      0
k8s Service *-postgresql        1428   ← все сироты
```

Каждая база представлена дважды: как синтетический `db:<driver>:<host>`
(связан, к нему идут все рёбра) и как k8s Service `town-db-postgresql`
(сирота). Это не отсутствие рёбер, а **дублирование сущностей** — тот же
класс расхождения, что `serves_traffic` до contract 2.4.

Развилка: либо связать представления явным ребром, либо признать k8s-Service
БД служебной точкой доступа и увести из app-scope.

## 3. Почему они вообще в знаменателе: stale_class не проставлен

```
stale_class IS NULL      2904 узла (58% всех service-узлов)
  из них в squad-*       2830
  в prod-* / preprod-*      0
```

Классификатор (`stale_classifier`) знает про суффиксы `-hl`, `-metrics`,
`-backup` и должен помечать их `expected_stale` — то есть выводить из
знаменателя. В prod и preprod он отрабатывает на 100%. В сквадах — на
половине узлов.

Причина в том, **кто** проставляет класс: `_refresh_stale_class_for_namespace`
вызывается только из `sync_namespace`, то есть в обходе `kg_topology_sync` по
namespace, которые вернул `_discover_namespaces` (живые namespace кластера).
При этом узлы трогают и другие синки — `updated_at` у NULL-строк свежий
(07:40 того же дня, то есть последний тик), а класса нет.

Второй вклад — мёртвые стенды:

```
namespace в графе      175
namespace в кластере   139
```

`squad-39-shared`, `squad-54-shared`, `squad-27-shared` — по 61 узлу каждый,
все с `stale_class IS NULL`, в кластере таких namespace **нет**. Снесённые
сквады остались в графе и продолжают тянуть знаменатель вниз.

## 4. Приложения: сигнал есть, но за `secretKeyRef`

Оставшиеся 672 — реальные сервисы (`notificator`, `analytics-store-service`,
`town-worker`, `chat-tasks-service`, `*-service-internal`). Ни одного в
prod: всё в сквадах и preprod.

У них богатые связочные env — но:

```
связочных env в preprod-kingdom2   151
  через secretKeyRef               134   (89%)
  литеральный value                 17   (11%)
  через configMapKeyRef              0
```

`kg_sync` читает `e.get("value")`, то есть видит 11% сигнала. Остальное
спрятано за ссылкой на Secret, и читать его ради построения графа нельзя —
там пароли и токены.

**Но имя переменной уже называет цель.** Именование в WO дисциплинировано:

| env | цель | вид ребра |
|---|---|---|
| `MESSAGE_DB_CONNECTION` | `message-db` | `uses_db` |
| `TOWN_DB_CONNECTION` | `town-db` | `uses_db` |
| `UPDATE_SERVICE_REST_ENDPOINT` | `update-service` | `calls` |
| `CURRENCY_RATE_SERVICE_URL` | `currency-rate-service` | `calls` |
| `SHARED_NATS_CONNECTION` | NATS | `uses_nats` (уже парсится) |

Проверка резолва логического имени в узел графа (8 целей из одного
namespace): **6 из 8 находят существующий узел**, БД — через суффикс
(`town-db` → `town-db-postgresql`). Не нашлись `mv-postgres-db` и
`currency-rate-service` — вероятно, внешние по отношению к кластеру.

Один namespace (preprod-kingdom2, ~20 деплойментов) даёт **62 кандидата
рёбер** к 13 уникальным целям.

## 5. Что делать, по убыванию отдачи

1. **Довести классификацию до всех узлов** (не только до тех, что попали в
   обход topology-sync) и вычистить namespace, которых нет в кластере.
   Отдача: до −77% orphan, ноль новых рёбер, ноль риска ложных связей.
2. **Решить дубль «БД = два узла»** — связать явным ребром либо увести
   k8s-Service БД из app-scope. Отдача: −21.7% orphan.
3. **Строить рёбра из ИМЁН связочных env**, не читая значения. Отдача:
   большая часть оставшихся 672 приложений. Риск — ложные рёбра при
   расхождении именования, поэтому нужен резолвер с явными правилами и
   пометкой `discovered_by=env_name_heuristic`, чтобы такие рёбра можно было
   отличить от наблюдаемых.

Пункты 1–2 меняют метрику, ничего не выдумывая: они убирают из знаменателя
то, что никогда не было топологией. Пункт 3 добавляет реальные связи, и
именно он требует осторожности — ребро, выведенное из имени переменной, это
гипотеза, а не наблюдение.

## Оговорка про цель «10%»

Считать её нужно per-env (см. `compute_orphan_stats_by_env`): на проде orphan
уже 13.8% при 160 узлах, тогда как 89% знаменателя — эфемерные сквады.
Агрегатная цифра описывает в основном связность стендов, живущих несколько
дней.
